=======================================

IMPLEMENTATION STATUS (ALREADY CODED)
=====================================

The application code is complete for:

- EUR 39.00 monthly PayPal subscription checkout

- server-created subscriptions (the browser cannot choose price, plan or hotel)
- server verification after PayPal approval
- cryptographically verified PayPal webhooks

==================================================

From this exact directory:

  C:\laragon\www\app_qualityfriend

run:

  docker compose exec app npx prisma migrate deploy

Then regenerate the Prisma client if your deployment/build process does not do
it automatically:

  docker compose exec app npx prisma generate

Migration owned by this project:

  prisma/migrations/20260901120000_add_paypal_subscriptions/migration.sql
  prisma/migrations/20260901130000_add_billing_configuration/migration.sql

The migration deliberately keeps existing hotels ACTIVE. New registrations
start as PENDING and must subscribe.

Business rule
-------------

- QualityFriend has one plan: EUR 39.00 per month.
- Registration creates the hotel and owner account, but the hotel starts with
  subscription status PENDING and cannot use the application yet.
- After registration, redirect the owner to /billing/subscribe.
- Only an ACTIVE subscription unlocks the software for every active user in
  that hotel tenant.
- Do not unlock access from a browser redirect or PayPal onApprove callback
  alone. The backend must verify the subscription with PayPal and process
  verified PayPal webhooks.

IMPORTANT OWNERSHIP RULE

Replace PROD-RETURNED-BY-PAYPAL below with the product ID:

$planBody = @{
  product_id = "PROD-RETURNED-BY-PAYPAL"
  name = "QualityFriend Monthly"
  description = "QualityFriend full access - EUR 39 per month"
  status = "ACTIVE"
  billing_cycles = @(

        interval_unit = "MONTH"
        interval_count = 1
      }
      tenure_type = "REGULAR"
      sequence = 1
      total_cycles = 0
      pricing_scheme = @{
        fixed_price = @{

          currency_code = "EUR"
        }
      }
    }
  )

    auto_bill_outstanding = $true
    payment_failure_threshold = 3
  }

$plan = Invoke-RestMethod `
  -Method Post `
  -Uri "https://api-m.sandbox.paypal.com/v1/billing/plans" `
  -Headers @{
    Authorization = "Bearer $accessToken"
    "PayPal-Request-Id" = "qualityfriend-eur-39-monthly-v1"

  -ContentType "application/json" `
  -Body $planBody

$plan.id

Copy the returned P-... value into .env:

PART 7 - REQUIRED APPLICATION FLOW
===================================

Registration:

1. Create hotel tenant and owner user in one database transaction.
2. Set subscription_status to PENDING.
3. Create the normal login session.
4. Redirect to /billing/subscribe instead of /dashboard.

Access guard:

1. Every protected page and API checks the hotel subscription status.
2. ACTIVE permits access.
3. Other statuses redirect to /billing/subscribe or /billing/status.
4. Always allow these routes while payment is pending:

   /billing/*
   /api/billing/*
   /api/paypal/webhook
   /api/logout
   /settings/account (optional)

5. The subscription belongs to the hotel tenant, not an individual employee.
   When the hotel is ACTIVE, its permitted users can access the application.

PayPal button page:

1. Load the PayPal JavaScript SDK with:

   client-id=NEXT_PUBLIC_PAYPAL_CLIENT_ID
   vault=true
   intent=subscription
   currency=EUR

2. createSubscription must use PAYPAL_PLAN_ID.

3. Send the hotel tenant UUID as PayPal custom_id. This is how the verified
   webhook is safely mapped back to the hotel.

4. onApprove sends subscriptionID to the backend.

5. The backend calls PayPal GET /v1/billing/subscriptions/{subscription_id}.

6. The backend verifies all of the following before updating local records:

   - The PayPal plan_id equals PAYPAL_PLAN_ID.
   - custom_id equals the authenticated hotel tenant ID.
   - The subscription belongs to the expected environment.
   - The returned status is valid.

7. Treat onApprove as pending confirmation. The verified webhook is the final
   authority for continued access.


PART 8 - CONFIGURE THE PAYPAL WEBHOOK
=====================================

The webhook must be publicly reachable over HTTPS. localhost cannot receive
real PayPal webhooks. Example production URL:

https://app.your-domain.com/api/paypal/webhook

In PayPal Developer Dashboard:

1. Open Apps & Credentials.
2. Select the Sandbox app.
3. Find Webhooks and select Add Webhook.
4. Enter the HTTPS webhook URL.
5. Subscribe to these events:

   BILLING.SUBSCRIPTION.ACTIVATED
   BILLING.SUBSCRIPTION.UPDATED
   BILLING.SUBSCRIPTION.SUSPENDED
   BILLING.SUBSCRIPTION.CANCELLED
   BILLING.SUBSCRIPTION.EXPIRED
   BILLING.SUBSCRIPTION.PAYMENT.FAILED
   BILLING.SUBSCRIPTION.RE-ACTIVATED
   PAYMENT.SALE.COMPLETED
   PAYMENT.SALE.REFUNDED
   PAYMENT.SALE.REVERSED

6. Save the webhook.
7. Copy its webhook ID into .env:

PAYPAL_WEBHOOK_ID=YOUR-SANDBOX-WEBHOOK-ID

The webhook route must verify every event by calling PayPal's webhook signature
verification API using PAYPAL_WEBHOOK_ID and the original PayPal transmission
headers. Never trust an unverified webhook body.

Return HTTP 2xx only after the event is safely recorded. PayPal retries failed
deliveries, so processing must be idempotent.

Official documentation:
https://developer.paypal.com/api/rest/webhooks/
https://developer.paypal.com/api/rest/webhooks/rest/
https://developer.paypal.com/api/rest/webhooks/event-names/


PART 9 - STATUS AND ACCESS MAPPING
==================================

PayPal event/status                  Local access
--------------------------------------------------------------
ACTIVATED                            Allow access (ACTIVE)
PAYMENT.SALE.COMPLETED               Keep access active; record payment
RE-ACTIVATED                         Allow access again
SUSPENDED                            Block access or apply chosen grace period
PAYMENT.FAILED                       Record failure; follow PayPal status
CANCELLED                            Block after the paid period ends
EXPIRED                              Block access
SALE REFUNDED / REVERSED             Flag for administrator review

Do not immediately erase hotel data when payment stops. Block application
access and retain data according to the contract and data-retention policy.

SECURITY RULES
==============

- Never commit .env.
- Never expose PAYPAL_CLIENT_SECRET to the browser.
- Never trust price, plan ID, hotel ID or subscription status sent by the UI.
- Never unlock access solely from onApprove or a return URL.
- Verify the PayPal subscription on the server.
- Verify every webhook signature.
- Store each PayPal event ID once to prevent duplicate processing.
- Keep an audit log for activation, suspension, cancellation and reactivation.
- Use HTTPS in production.
- Keep separate Sandbox and Live credentials.
- Back up subscription and payment-event database records.
